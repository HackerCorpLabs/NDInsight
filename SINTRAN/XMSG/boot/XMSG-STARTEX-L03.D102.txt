@CC  THE CHAT SERVER
@CC
@CC  A plain @RT is enough on a COLD BOOT - measured 2026-08-23. The RT
@CC  description and its segment survive a reboot, and XMSG has already
@CC  been started above, so the server comes up against a live kernel.
@CC
@CC  The "RT-LOAD it again" rule is about XMSG being restarted UNDERNEATH
@CC  a server that is already running. That cannot happen here: order
@CC  saves us, XMSG first and the server after.
@CC
@CC  COSMOS starts after this file and does NOT touch XMSG - it restarts
@CC  XFTRAD, spooling and the file server - so the chat server is safe.
@CC
@CC  D103's file has no line like this one because nobody has established
@CC  that D103 has a CHATSER. It is NOT known to be missing - the check
@CC  that seemed to say so was a mis-typed command, not a measurement.
@CC ====================================================================
@RT CHATSER
@CC
@CC ====================================================================
@CC  THE TRUNK TO THE OTHER MACHINE
@CC
@CC  WITHOUT THIS, FEDERATION DOES NOT SURVIVE A REBOOT. Measured
@CC  2026-08-24: the server keeps NO trunk file. It opens a log and the
@CC  room histories and nothing else, so a peer row lives only as long as
@CC  the program does. On D100, LIST-TRUNKS answered "102 up" on a machine
@CC  booted that same morning ONLY because somebody had typed START-TRUNK
@CC  by hand. Nothing in any boot file started one.
@CC
@CC  START-TRUNK only has to REGISTER the peer. It does not have to reach
@CC  it. The server ages a trunk and dials it again by itself, with the
@CC  idle sleep as the clock, so running this before the other machine is
@CC  up is fine - and at boot the other machine usually is not up.
@CC
@CC  BOTH MACHINES START THEIR OWN END. One side is enough to carry
@CC  traffic, but starting both removes any dependence on which machine
@CC  finished booting first.
@CC
@CC  THE RACE THIS DOES NOT SOLVE, said plainly: @RT CHATSER returns as
@CC  soon as the RT program is started, not when it has claimed its admin
@CC  port, and CHAT-MON talks to that port. If it gets there first the
@CC  START-TRUNK is lost. How long the server needs has NOT been measured.
@CC  That is why LIST-TRUNKS follows: whatever happened, the boot log says
@CC  so, and a missing row is visible instead of silent.
@CC ====================================================================
@CC  ---- WHAT THIS MACHINE IS CALLED ----------------------------------
@CC
@CC  SET-NAME is NOT written to disk by the server, deliberately - so it
@CC  belongs here, beside the trunks, in the one file that describes this
@CC  machine. Without it the machine comes back as D<number>, which is
@CC  exactly how everything behaved before names existed. Nothing breaks;
@CC  the name is simply missing.
@CC
@CC  IT MUST COME BEFORE THE TRUNKS. The name travels on the trunk Hello,
@CC  so a trunk started first says hello with no name and the peer learns
@CC  one only on the NEXT exchange.
@CC
@CC  ---- AND WHY THREE TRUNKS, NOT TWO --------------------------------
@CC
@CC  These machines are a TRIANGLE now, not a chain. Two reasons, both
@CC  measured 2026-08-26:
@CC
@CC    A MACHINE ONLY LEARNS NAMES FROM ITS DIRECT PEERS. On the chain a
@CC    line relayed D103 -> D100 -> D102 arrived on D102 as @D103 and not
@CC    @SKOGEN, because D102 had no peer row for 103 to look a name up in.
@CC
@CC    DEDUP CANNOT BE EXERCISED ON A CHAIN. There is one path between any
@CC    two machines, so dupe reads 0 whatever the code does - and a broken
@CC    implementation reads 0 too. The third trunk is what made it say 1.
@CC
@CC  D100's boot file was ALSO missing START-TRUNK 103 entirely, which is
@CC  why D103 was never registered here from a cold start.
