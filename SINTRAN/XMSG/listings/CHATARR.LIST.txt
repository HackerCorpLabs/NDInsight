     1          % ===========================================================================
     2          % CHATARR - what the client does when a message ARRIVES.
     3          %
     4          % Split out of CHAT.PLNC on 2026-08-28. It is the same code, moved, so that a
     5          % change to it costs one short compile instead of twenty minutes on a 6586-line
     6          % source. Nothing here was rewritten.
     7          %
     8          % WHY THIS SUBJECT AND NOT ANOTHER. It is the largest single thing in the
     9          % client - 918 lines across three routines - and it touches the fewest names it
    10          % does not own: 45 cross the boundary and NOT ONE PAIR of them agrees in its
    11          % first seven characters, which is all a BRF entry carries. Two exports that do
    12          % agree are ONE name to the linker and it does not warn; it resolves every
    13          % import to whichever it met first.
    14          %
    15          % HOW THE HALVES FIT
    16          %
    17          %   CHAT     owns the state and the drawing, and EXPORTs them.
    18          %   CHATARR  IMPORTs those, and EXPORTs the single entry point showArrived.
    19          %
    20          % The forms below are the ones proved on D100 by SPLITA/SPLITB on 2026-08-26 -
    21          % a scalar, a BYTES ARRAY and a routine all cross a BRF boundary and refer to
    22          % ONE copy of the data, not two. That test exists because the manual's own
    23          % example only covers the scalar.
    24          %
    25          % THE ORDER OF THE LINK MATTERS: the program first, then what satisfies it.
    26          % CHATARR is loaded after CHAT and before the libraries.
    27          % ===========================================================================
    28          MODULE chatarr
    29          
    30              % ---- the one thing this module hands back ------------------------------
    31              EXPORT showArrived

   111              % THE INNER HALF. Everything it renders goes into whatever window is
   112              % current, which is exactly what it did before windows existed - it is the
   113              % wrapper below that decides which window that is.
   114              ROUTINE VOID, BOOLEAN : uiArrivedInner
   115                  % Which conversation window a private message belongs in. Zero means
   116                  % there was no room for one - see winFor.
   117                  INTEGER : dirWin
   118                  INTEGER : kind
   119                  INTEGER : nameLength
   120                  INTEGER : textLength
   121                  INTEGER : textAt
   122          
   123                  IF NOT screenOn THEN
   124                      FALSE RETURN
   125                  ENDIF
   126          
   127                  cmKind(inBuf) =: kind
   128                  cmNmLen(inBuf) =: nameLength
   129          
   130                  % THE SAME LENGTH GUARD THE LINE RENDERER USES, and for the same
   131                  % reason: nameLength is one byte and can say 255, which would read
   132                  % past the end of a message that never held that much.
   133                  %
   134                  % IT STAYS AHEAD OF cmTxLen ON PURPOSE. cmTxLen reads the two bytes at
   135                  % nameLength + 2, so calling it before this guard would do exactly the
   136                  % over-read the guard exists to prevent - the library clamps what it
   137                  % WRITES, and cannot know how many bytes actually arrived.
   138                  IF 2 + nameLength + 1 > readLength THEN
   139                      TRUE RETURN
   140                  ENDIF
   141                  cmTxLen(inBuf) =: textLength
   142                  cmTxAt(inBuf) =: textAt
   143          
   144                  % ---- somebody spoke -------------------------------------------
   145                  % A ZERO-LENGTH FIELD WOULD MAKE A REVERSED SUBARRAY - inBuf(2:1) -
   146                  % and PLANC checks no bounds, so it would be handed whatever that
   147                  % happens to mean. Both are built as a notice instead, which is also
   148                  % the more useful thing to show.
   149                  IF kind = kSaid THEN
   150                      uiSaid(2, nameLength, textAt, textLength)
   151                      TRUE RETURN
   152                  ENDIF
   153          
   154                  % REPLAYED HISTORY is drawn exactly like live traffic here, and that
   155                  % is a deliberate difference from the line renderer, which marks it
   156                  % with a bar. On a screen the lines above the newest ARE the past, so
   157                  % the mark says nothing the position does not.
   158                  IF kind = kHist THEN
   159                      uiSaid(2, nameLength, textAt, textLength)
   160                      TRUE RETURN
   161                  ENDIF
   162          
   163                  % ---- a direct message, and it stays marked ---------------------
   164                  %
   165                  % The stars are not decoration. A reply typed as an ordinary line goes
   166                  % to the whole room, so a private message that looks like room traffic
   167                  % is a privacy failure caused entirely by the display.
   168                  % A PRIVATE MESSAGE GETS ITS OWN WINDOW, one per person.
   169                  %
   170                  % It used to go in the room's buffer marked with stars. That worked,
   171                  % but it put one person's private conversation in the middle of
   172                  % everybody else's traffic, where it scrolls away behind lines that
   173                  % have nothing to do with it - and the stars had to carry the whole
   174                  % weight of saying "this one is not what it looks like".
   175                  %
   176                  % IF EVERY WINDOW IS TAKEN IT GOES IN THE ROOM, exactly as before.
   177                  % winFor answers zero for that, and the old path is still right there
   178                  % as the fallback rather than being an error case somebody has to
   179                  % have thought about.
   180                  IF kind = kDirGot THEN
   181                      winFor(2, nameLength) =: dirWin
   182                      IF dirWin > 0 THEN
   183                          putInWin(dirWin, 2, nameLength, textAt, textLength)
   184                      ELSE
   185                          uiClear
   186                          uiWord('*(')
   187                          uiFrom(2, nameLength)
   188                          uiWord(') ')
   189                          uiFrom(textAt, textLength)
   190                          uiNotice
   191                      ENDIF
   192                      TRUE RETURN
   193                  ENDIF
   194          
   195                  % YOUR OWN HALF OF THE CONVERSATION, in the same window as their half.
   196                  % Without this a window would hold one side of a conversation, which
   197                  % reads as a series of unanswered messages.
   198                  %
   199                  % The server sends this WITHOUT the text - it only confirms who it
   200                  % went to - so what is shown is the line as it was typed, which the
   201                  % send path kept for exactly this.
   202                  IF kind = kDirSent THEN
   203                      winFor(2, nameLength) =: dirWin
   204                      IF dirWin > 0 THEN
   205                          putSentInWin(dirWin)
   206                      ELSE
   207                          uiClear
   208                          uiWord('sent to ')
   209                          uiFrom(2, nameLength)
   210                          uiNotice
   211                      ENDIF
   212                      TRUE RETURN
   213                  ENDIF
   214          
   215                  IF kind = kDirBad THEN
   216                      uiClear
   217                      uiWord('NOT sent to ')
   218                      uiFrom(2, nameLength)
   219                      uiWord(': ')
   220                      uiFrom(textAt, textLength)
   221                      uiNotice
   222                      TRUE RETURN
   223                  ENDIF
   224          
   225                  % ---- who came and went -----------------------------------------
   226                  IF kind = kJoined THEN
   227                      % ONE MORE, WITHOUT ASKING. Asking the server on every arrival
   228                      % would put a letter on the wire for every join in the room, and
   229                      % the next /who corrects any drift anyway.
   230                      hereCount + 1 =: hereCount
   231                      uiClear
   232                      uiFrom(2, nameLength)
   233                      uiWord(' has joined')
   234                      uiNotice
   235                      TRUE RETURN
   236                  ENDIF
   237          
   238                  IF kind = kLeft THEN
   239                      % ONE FEWER, AND NEVER BELOW ZERO. A leave can arrive for somebody
   240                      % this client never saw join - it joined after them - and counting
   241                      % down past zero would show a negative in the status line.
   242                      IF hereCount > 0 THEN
   243                          hereCount - 1 =: hereCount
   244                      ENDIF
   245                      uiClear
   246                      uiFrom(2, nameLength)
   247                      uiWord(' has left')
   248                      uiNotice
   249                      TRUE RETURN
   250                  ENDIF
   251          
   252                  % A RENAME CARRIES THE NEW NAME IN THE NAME FIELD and the old one as
   253                  % the text - the order that is easiest to get backwards, which is why
   254                  % the C# golden test pins it.
   255                  IF kind = kRenOk THEN
   256                      uiClear
   257                      uiFrom(textAt, textLength)
   258                      uiWord(' is now ')
   259                      uiFrom(2, nameLength)
   260                      uiNotice
   261                      TRUE RETURN
   262                  ENDIF
   263          
   264                  % ---- the room itself -------------------------------------------
   265                  %
   266                  % The TOPIC answer names the ROOM in the name field where a nickname
   267                  % normally sits, so the name is not printed as a speaker here.
   268                  IF kind = kTopic THEN
   269                      % KEEP IT BEFORE PRINTING IT. The header shows the topic, and a
   270                      % message that is only printed is gone the moment the next line
   271                      % arrives - which is exactly why setting a topic changed nothing in
   272                      % the header until now. Done for BOTH meanings below: an asked-for
   273                      % topic and one somebody set are the same fact about the room.
   274                      setTopic(textAt, textLength)
   275          
   276                      % ONE KIND, TWO MEANINGS, and only this client knows which it is
   277                      % looking at. An ASKED-FOR topic is an answer to a question nobody
   278                      % else heard; a topic somebody SET is news for the whole room. The
   279                      % wire cannot tell them apart - the server sends the same kind - so
   280                      % the flag set when /topic was typed with no argument is what
   281                      % decides, and it is cleared whichever way this goes.
   282                      IF askedTopic THEN
   283                          FALSE =: askedTopic
   284                          IF textLength > 0 THEN
   285                              panelAnswer('the topic', textAt, textLength)
   286                          ELSE
   287                              panelClear
   288                              panelAdd('the topic')
   289                              panelAdd(' ')
   290                              panelAdd('  none set')
   291                              drawPanel
   292                          ENDIF
   293                          TRUE RETURN
   294                      ENDIF
   295          
   296                      uiClear
   297                      uiWord('topic: ')
   298                      IF textLength > 0 THEN
   299                          uiFrom(textAt, textLength)
   300                      ELSE
   301                          uiWord('none set')
   302                      ENDIF
   303                      uiNotice
   304                      TRUE RETURN
   305                  ENDIF
   306          
   307                  % ---- answers to a question, all one shape ----------------------
   308                  %
   309                  % who / everybody / rooms / map are readable text built by the server
   310                  % and are not parsed by anything here. They wrap across rows exactly
   311                  % as a long sentence does.
   312                  IF kind = kWho THEN
   313                      % THE COUNT IS TAKEN FROM THE ANSWER, not kept by this client.
   314                      % Whatever the server says is right, and it is right again every
   315                      % time somebody asks - so a count that has drifted repairs itself
   316                      % rather than needing to be got right for ever.
   317                      countNames(textAt, textLength) =: hereCount
   318          
   319                      % THE ONE THIS CLIENT ASKED FOR GOES IN A PANEL; the one it asked
   320                      % for ITSELF on the way in does not. Without that test the screen
   321                      % would open a window over the room the moment you joined, which
   322                      % nobody asked for and which would have to be dismissed before the
   323                      % first line could be read.
   324                      IF askedWho THEN
   325                          FALSE =: askedWho
   326                          panelAnswer('who is here', textAt, textLength)
   327                      ENDIF
   328                      TRUE RETURN
   329                  ENDIF
   330          
   331                  IF kind = kAllWho THEN
   332                      FALSE =: askedWho
   333                      panelAnswer('everybody, every room', textAt, textLength)
   334                      TRUE RETURN
   335                  ENDIF
   336          
   337                  IF kind = kRooms THEN
   338                      panelAnswer('rooms', textAt, textLength)
   339                      TRUE RETURN
   340                  ENDIF
   341          
   342                  IF kind = kMap THEN
   343                      panelAnswer('the machines', textAt, textLength)
   344                      TRUE RETURN
   345                  ENDIF
   346          
   347                  IF kind = kReject THEN
   348                      uiClear
   349                      uiWord('refused: ')
   350                      uiFrom(textAt, textLength)
   351                      uiNotice
   352                      TRUE RETURN
   353                  ENDIF
   354          
   355                  % kWelcome is NOT taken here. It sets serverMagic, joined and the
   356                  % machine name, and all of that lives in showArrived - so it falls
   357                  % through on purpose and the line renderer's own branch runs. Its
   358                  % printing goes to a screen that is about to be drawn over, which
   359                  % costs nothing.
   360                  %
   361                  % ANY OTHER KIND ALSO FALLS THROUGH, which is the right default: an
   362                  % unknown kind reaching the line renderer prints something a person
   363                  % can report, and reaching this one would vanish in silence.
   364                  FALSE RETURN
   365              ENDROUTINE
   366          
   367              % =====================================================================
   368              % WHICH WINDOW AN ARRIVING MESSAGE BELONGS IN
   369              %
   370              % A ROOM LINE ALWAYS GOES IN WINDOW 1, whatever is on screen. Without
   371              % this, reading a private conversation would quietly fill THAT window with
   372              % the room's traffic - the room would appear to have moved, and going back
   373              % to it would show a gap where the lines should be.
   374              %
   375              % A private message places itself, because only the handler knows whose
   376              % conversation it is; those two kinds are left alone here.
   377              %
   378              % THE UNREAD COUNT IS THE DIFFERENCE IN LINES, not one per message. A long
   379              % line becomes several cache lines, and a reader who sees "3" and finds one
   380              % sentence learns not to trust the number.
   381              % =====================================================================
   382              ROUTINE VOID, BOOLEAN : uiArrived
   383                  INTEGER : prev
   384                  INTEGER : before
   385                  INTEGER : grew
   386                  INTEGER : what
   387                  BOOLEAN : handled
   388          
   389                  % READ FROM inBuf, not passed in. The inner routine reads its own kind
   390                  % the same way from the same byte, so there is no second copy that
   391                  % could disagree with it.
   392                  cmKind(inBuf) =: what
   393                  curWin =: prev
   394          
   395                  IF what = kDirGot OR what = kDirSent THEN
   396                      uiArrivedInner =: handled
   397                      handled RETURN
   398                  ENDIF
   399          
   400                  IF prev = 1 THEN
   401                      uiArrivedInner =: handled
   402                      handled RETURN
   403                  ENDIF
   404          
   405                  % Somebody is reading a conversation. Step into the room, put the line
   406                  % where it belongs, and step straight back out.
   407                  winSave
   408                  winUse(1)
   409                  cacheCount =: before
   410                  uiArrivedInner =: handled
   411                  cacheCount - before =: grew
   412                  winSave
   413                  winUse(prev)
   414          
   415                  IF grew > 0 THEN
   416                      winUnread(1) + grew =: winUnread(1)
   417                  ENDIF
   418                  handled RETURN
   419              ENDROUTINE
   420          
   421          
   422              ROUTINE VOID, VOID : showArrived
   423                  INTEGER : kind, nameLength, textLength, textAt, i
   424                  % Only the screen path uses this - the /who it asks for on the way in.
   425                  INTEGER : length
   426                  % Only used by the kRenOk branch: is this rename about US?
   427                  BOOLEAN : sameAsOurs
   428                  INTEGER : newLen
   429          
   430                  % ON A SCREEN TERMINAL THE RENDERER TAKES IT FIRST.
   431                  %
   432                  % uiArrived answers FALSE when it has not dealt with the message -
   433                  % which is every kind on a printing terminal, and the welcome and any
   434                  % unknown kind on a screen one - and then everything below runs exactly
   435                  % as it always has. THE LINE RENDERER IS NOT TOUCHED BY THIS, which is
   436                  % what makes it safe: it stays the reference for what should be shown
   437                  % and the fallback for a terminal that cannot address its cursor.
   438                  IF uiArrived THEN
   439                      RETURN
   440                  ENDIF
   441          
   442                  cmKind(inBuf) =: kind
   443                  cmNmLen(inBuf) =: nameLength
   444          
   445                  % THE JOIN IS ONE STEP, and a two-step handshake used to live here.
   446                  %
   447                  % It was added on the reading that "sending the join through XROUT does
   448                  % not put the nickname in front of the server" - that the server's
   449                  % connection port is handed a bare 4-byte connect, so a kHello reply was
   450                  % needed before the nickname could be sent. That reading was WRONG, and
   451                  % it was wrong because the SERVER was reading the wrong bytes: a letter
   452                  % arrives with its XSLET header still attached, and the server was
   453                  % parsing the header's serial number as a message kind.
   454                  %
   455                  % The nickname was in the first letter the whole time. sendJoin writes it
   456                  % after the header and the Programmer Guide is explicit that XROUT
   457                  % forwards it untouched. The server's WELCOME is the answer that hands
   458                  % over the magic number, which is all this side ever needed. See the
   459                  % header skip in CHATSV.PLNC for the layout and the manual reference.
   460                  %
   461                  % Nothing replaces this block: the welcome below already sets
   462                  % serverMagic, and always did.
   463          
   464                  % ---- TRUST NOTHING THAT ARRIVED, ON THIS SIDE TOO ------------------
   465                  % The server checks exactly these three things before it reads a name or
   466                  % a text; this side did not, and the reasoning is identical. inBuf holds
   467                  % 256 bytes and PLANC checks no array bound:
   468                  %
   469                  %   nameLength is ONE BYTE, so it can say 255. The name loop would then
   470                  %   read inBuf(2)..inBuf(256) - past the end - and textAt would already
   471                  %   be 257 before any text was touched.
   472                  %
   473                  %   textLength is TWO BYTES, so it can say 65535, and the text loop
   474                  %   would walk tens of thousands of bytes off the end of the array.
   475                  %
   476                  %   A SHORT message is the quieter half: without testing against
   477                  %   readLength the loops print whatever the previous, longer message
   478                  %   left behind in inBuf.
   479                  %
   480                  % "The server would never send that" is not a reason. A truncated
   481                  % message does it by accident, and a client that only survives a
   482                  % well-behaved peer is not one worth writing.
   483                  % Both tests are against readLength, which the read below clamps to the
   484                  % size of inBuf - so a field that fits the MESSAGE also fits the ARRAY.
   485                  IF 2 + nameLength + 1 > readLength THEN
   486                      RETURN
   487                  ENDIF
   488          
   489                  % READ ONLY AFTER THE GUARD ABOVE - cmTxLen fetches the two bytes at
   490                  % nameLength + 2, which is the over-read that guard prevents.
   491                  cmTxLen(inBuf) =: textLength
   492                  cmTxAt(inBuf) =: textAt
   493          
   494                  IF textAt + textLength > readLength THEN
   495                      RETURN
   496                  ENDIF
   497          
   498                  % The WELCOME is what reveals the server's address: everything after it
   499                  % goes straight there.
   500                  IF kind = kWelcome THEN
   501                      senderMagic =: serverMagic
   502                      TRUE =: joined
   503          
   504                      % THE WELCOME'S TEXT IS THE MACHINE THIS CLIENT IS ON. It was
   505                      % always empty before, so a server that has not been upgraded
   506                      % simply leaves this empty and the screen shows the name alone.
   507                      IF textLength > 0 THEN
   508                          textLength =: lenMyMach
   509                          IF lenMyMach > 16 THEN
   510                              16 =: lenMyMach
   511                          ENDIF
   512                          FOR i IN 1:lenMyMach DO
   513                              inBuf(textAt + i - 1) =: myMachine(i - 1)
   514                          ENDFOR
   515          
   516                          % REDRAW THE WHOLE FRAME, because the corner is painted by
   517                          % drawAll and drawAll ran before this arrived - the join is
   518                          % sent first and the welcome answers it. Without this the
   519                          % corner says TESTER for the rest of the session on a machine
   520                          % that has a perfectly good name.
   521                          %
   522                          % Once per session, so the cost does not matter.
   523                          IF screenOn THEN
   524                              drawAll
   525                              flush
   526                          ENDIF
   527                      ENDIF
   528          
   529                      % ASK WHO IS HERE, ONCE, so the status line starts out TRUE.
   530                      %
   531                      % The welcome is the first moment there is a seat to ask from. Only
   532                      % on a screen: the line renderer has no status line to fill, and an
   533                      % unasked-for /who answer printed at a user who did not type one
   534                      % would be noise.
   535                      IF screenOn THEN
   536                          buildOwn(kWho, 0) =: length
   537                          sendToServer(length)
   538                      ENDIF
   539          
   540                      % SAY WHO YOU ARE, ONCE, AND ONLY NOW THAT IT IS TRUE. The server
   541                      % has accepted the name, so this is a fact rather than a hope - see
   542                      % the note in setupName for what printing it early looked like.
   543                      % ON A SCREEN THIS GOES IN THE ROOM, NOT TO THE CURSOR.
   544                      %
   545                      % MEASURED on D100 2026-08-26: printed with OUTPUT while the frame
   546                      % was already up, it landed ON THE INPUT ROW -
   547                      %
   548                      %     > you are TESTER on FJELL  (/nick to change)
   549                      %
   550                      % because OUTPUT writes wherever the cursor happens to be, and the
   551                      % cursor is parked on the input line by drawInput. It used to be
   552                      % harmless: the welcome arrived before the first paint and was
   553                      % simply drawn over. It is not harmless now that the welcome also
   554                      % triggers a repaint.
   555                      %
   556                      % The corner already says TESTER@FJELL, so this is only the
   557                      % sentence - and a sentence belongs with the other sentences.
   558                      IF screenOn THEN
   559                          % announceWelcome LIVES IN CHAT.PLNC NOW - 2026-09-01.
   560                          %
   561                          % MEASURED: with the flag it reads EXPORTed and read back
   562                          % through an IMPORT here, this branch fired TWICE for one
   563                          % real join on a client that never touched the room a second
   564                          % time - the flag AND cacheCount both read back as their
   565                          % INITIAL values on the second firing. A ROUTINE call across
