     1          % ---------------------------------------------------------------------------
     2          % CHATSV - the chat room server, as a SINTRAN RT program.
     3          %
     4          % COMPILED AND RUN ON D100, 2026-08-18. It served a real room to two real
     5          % clients on two terminals, and the round trip both ways is in the log:
     6          %
     7          %     routed letter    rcv st= 0  t= 2  len= 25   hdr ends= 16   parse k=1 nlen=5
     8          %     ordinary msg     rcv st= 0  t= 1  len= 14   parse k=4 nlen=5   slot now= 1
     9          %
    10          % Those two lines came from diagnostics that have since been taken out; what
    11          % each of them proved is written beside the code it proved it about.
    12          %
    13          % Every XMSG routine below, and the way it is CALLED, is taken from the routine
    14          % reference and worked examples in
    15          %     Operations/Cosmos/ND-60164-3-EN COSMOS Programmer Guide.md
    16          % rather than from analogy. Four things that reference corrected, each of which
    17          % would have cost a compile or worse:
    18          %
    19          %   XMPOPNM -> XMPOPCN   a room has SEATS, and the free-connection counter
    20          %                        belongs to a CONNECTION port. With XMPOPNM the limit is
    21          %                        silently absent while the C# side still enforces it.
    22          %   XMPFFRE -> XMPFREL   XMPFFRE does not exist.
    23          %   XMPFREA/XMPFWRI      take NO message identifier - they act on the CURRENT
    24          %                        message, as XMPFSND sends it.
    25          %   ADDR(buf)            is not enough. The guide's own examples write
    26          %                        addr(buf(0)) FORCE XMUSERADDRESS.
    27          %
    28          % And every call RETURNS its status - the examples all end "=: returnStatus".
    29          % That is how the statuses below are checked; XMOK is zero, from XMP-B02:DEFS.
    30          %
    31          % THE MESSAGE FORMAT IS OURS. We chose it; no ND ever sent one, so no capture
    32          % will ever confirm it and Xmsg.Chat/ChatMessage.cs plus its tests are its only
    33          % specification. The rules below are a transcription of Xmsg.Chat/ChatRoom.cs,
    34          % which has the tests that say what "correct" means.
    35          %
    36          %     byte 0      kind          1 Join 2 Welcome 3 Reject 4 Say 5 Said
    37          %                               6 Leave 7 Joined 8 Left 9 Rename 10 Renamed
    38          %     byte 1      nickname length
    39          %     bytes 2..   nickname
    40          %     then        2 bytes text length, big endian
    41          %     then        the text
    42          %
    43          % THE BYTE LAYOUT IS PINNED IN C#, and this file must agree with it by hand.
    44          % SRC/Xmsg.Chat.Tests/ChatMessageGoldenBytesTests.cs holds the exact bytes of a
    45          % Said, a Renamed, a Join and a 300-character line. There is no shared code
    46          % between that and this - only those goldens - so if the layout ever changes,
    47          % both sides change in the SAME commit or they disagree in silence.
    48          %
    49          %
    50          % THREE CORRECTIONS FROM APPENDIX G, the guide's own sample CLIENT and SERVER:
    51          %
    52          %   flags are 2**BIT      XFWTF is a BIT POSITION (15), not a flags word. The
    53          %                         samples both write "2**XFWTF =: FLAGS". Passing 15
    54          %                         would set bits 0,1,2,3 - four unrelated options - and
    55          %                         the wait would simply not happen.
    56          %   XMMSGIDENTIFIER       the message-identifier type, with two M's. Written
    57          %                         "XMMSGIDENTIFIER: MSGIDENT" in the sample.
    58          %   XMUSERADDRESS         and the address idiom is
    59          %                         ADDR(BUF(0)) FORCE XMUSERADDRESS. ROUND brackets -
    60          %                         the guide prints square ones and PLANC F rejects
    61          %                         them with EXPECTS ")" ILLEGAL SYNTAX "[".
    62          %
    63          % ---------------------------------------------------------------------------
    64

   750    (90)      % THERE IS NO ELEVENTH KIND, and the reason is worth keeping.
   751    (91)      %
   752    (92)      % A kHello was invented here on 2026-08-18 to answer the connect on its own,
   753    (93)      % on the belief that a connection port is handed "4 bytes with byte 0 = 0"
   754    (94)      % and that the joiner's nickname could only follow as a second, ordinary
   755    (95)      % message. That belief was wrong, and it was wrong because this program was
   756    (96)      % reading the WRONG BYTES: the connect arrives with the XSLET letter header
   757    (97)      % still in front of it, and byte 0 of that header is the serial number.
   758    (98)      %
   759    (99)      % The nickname was in the very first arrival all along. See the header skip
   760   (100)      % in the receive loop for the layout and the manual reference. The join is
   761   (101)      % ONE step, exactly as the Programmer Guide describes it: the letter carries
   762   (102)      % the user data, the server answers it, and "thereby gives away its own
