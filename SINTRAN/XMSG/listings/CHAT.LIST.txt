     1          % ---------------------------------------------------------------------------
     2          % CHAT - the chat client, an ordinary SINTRAN PROG.
     3          %
     4          % COMPILED AND RUN ON D100, 2026-08-18. Two terminals, one room, both
     5          % directions:
     6          %
     7          %     @CHAT
     8          %     CHAT: joining, type and press return
     9          %     RONNY: HELLO FROM A REAL ND
    10          %
    11          % This header said "NOT COMPILED, NOT RUN" for as long as that was true and for
    12          % a while after it stopped being true, which is its own small lesson - see the
    13          % note at the end of the file about what else went stale with it.
    14          %
    15          % Run it with @CHAT. It joins CHAT-LOBBY on the local system, then sits in a
    16          % loop watching two things at once: the keyboard and the port. Type a line and
    17          % it is said to the room; anything the room says appears on the screen.
    18          %
    19          % THE TWO-THINGS-AT-ONCE PROBLEM, which looked like the hard part, is solved by
    20          % two facts from the manuals rather than by any trickery:
    21          %
    22          %   XMPFRCV WITHOUT XFWTF returns AT ONCE rather than waiting, so the port can
    23          %   be polled. A message arrived exactly when the status is POSITIVE: the
    24          %   constants file says the message TYPE is the successful status from XFRCV,
    25          %   and the types run XMTNO=1 to XMTPS=6 while every user error is negative.
    26          %
    27          %   TerminalNoWait (MON 307B) switches the terminal to no-wait, after which
    28          %   InByte (MON 1B) returns at once too. Device 1 is your own terminal.
    29          %
    30          % So no second RT program, no shared buffer and no timeouts: an ordinary loop.
    31          %
    32          % AND WHAT DOES InByte GIVE BACK WHEN NOTHING WAS TYPED? Not a character:
    33          % "In No Wait, the program does not wait for input or output to complete.
    34          % Monitor calls like InByte return ERROR CODE 3 instead." - the NoWaitSwitch
    35          % entry in the Monitor Calls manual. In PLANC a monitor-call error arrives as a
    36          % ROUTINEERROR, handled with ON ROUTINEERROR DO ... ENDON and read from ErrCode,
    37          % which is the form that manual's own PLANC example for InByte uses.
    38          %
    39          % An earlier version of this loop assumed InByte returned some value that would
    40          % mask to 31 or below and could be ignored. That was a guess and it was wrong.
    41          %
    42          % THE PARITY TRAP, and the Monitor Calls manual warns about it in so many
    43          % words: terminal input sets bit 7 as an even-parity bit, so carriage return
    44          % arrives as 141, NOT 13. Compare against 13 and the client never sees the user
    45          % press return, and looks hung rather than wrong. Everything read is masked
    46          % with 127 before it is looked at.
    47          %
    48          % Sending the join is the letter sequence from the COSMOS Programmer Guide's
    49          % own worked example (page 99): XMPBLET builds an XSLET letter header in a
    50          % local buffer, XMPFGET reserves an XMSG buffer, XMPFWRI writes the header into
    51          % it and then writes OUR data after it, and XMPROUT sends the whole thing via
    52          % XROUT. The room's name is looked up by XROUT; we never need its address.
    53          % That trailing-data arrangement is exactly how the join carries a nickname.
    54          %
    55          % THREE CORRECTIONS FROM APPENDIX G, the guide's own sample CLIENT and SERVER:
    56          %
    57          %   flags are 2**BIT      XFWTF is a BIT POSITION (15), not a flags word. The
    58          %                         samples both write "2**XFWTF =: FLAGS". Passing 15
    59          %                         would set bits 0,1,2,3 - four unrelated options - and
    60          %                         the wait would simply not happen.
    61          %   XMMSGIDENTIFIER       the message-identifier type, with two M's. Written
    62          %                         "XMMSGIDENTIFIER: MSGIDENT" in the sample.
    63          %   XMUSERADDRESS         and the address idiom is
    64          %                         ADDR(BUF(0)) FORCE XMUSERADDRESS.
    65          %
    66          %                         ROUND brackets. The guide's sample prints this with
    67          %                         square ones and it does not compile: PLANC F answers
    68          %                         EXPECTS ")" ILLEGAL SYNTAX "[" and then INVALID
    69          %                         PARAMETER LIST for the call around it. Array indexing
    70          %                         in this language uses parentheses like everything
    71          %                         else. Trust the compiler over the typesetting.
    72          %
    73          % ---------------------------------------------------------------------------
    74          
    75          % THE INCLUDE NAMES ON THIS MACHINE, and they are NOT the manual's.
    76          % The COSMOS guide says XMP:DEFS and XMP:IMPT. Neither exists on D100:
    77          % the constants ship as (UTILITY)XMSG-PL-VALUES-L:INCL, and there is no
    78          % :IMPT file at all - the whole UTILITY user was listed to be sure. So the
    79          % routine and type declarations are ours, built from the guide's reference
    80          % tables and the PLANC manual's declaration syntax.
    81          %
    82          % Our own include is called XMPIMP:INCL on the machine, short, because our
    83          % file transfer cannot carry a filespec longer than 13 characters. The repo
    84          % keeps it under the readable name XMSG-PL-IMPORT.INCL and the build renames
    85          % it on the way over; do not "fix" this to the long name or the transfer
    86          % silently has nothing to send.
    87          MODULE chat
    88          
    89          % THE INCLUDES GO INSIDE THE MODULE, and this is not a style choice. Placed
    90          % above MODULE they are compiled into the outer scope, the module body cannot
    91          % see them, and every call fails with NOT PREVIOUSLY DECLARED "XMPFOPN" while
    92          % the include's own lines draw no diagnostic at all - so the declarations look
    93          % accepted and are simply not there. Measured on D100: 33 diagnostics, none of
    94          % them on the include. The COSMOS guide's appendix G sample has them after
    95          % MODULE for exactly this reason.
    96          % THE REAL COSMOS BINDING, installed from ND-10609 on 1998-08-17 (2026-08-17
    97          % our time) by the product's own COS-LIB-IN-B02:PROG. These are the genuine ND
    98          % files, not our transcription:
    99          %
   100          %   XMP-B02:DEFS   the constants, including the ones that exist nowhere else -
   101          %                  XMOK=0, and the XMX... standard status values. Its own
   102          %                  comment records that the library REMAPS the kernel's status:
   103          %                  "NOTE change from XMSG OK=1".
   104          %   XMP-B02:IMPT   the types and the IMPORT declarations for 54 routines.
   105          %   XMP-100-1-B02:BRF  the code behind those names, linked in by CHATCC:MODE.

   107          % DO NOT ALSO INCLUDE XMSG-PL-VALUES-L:INCL. The two files share 184 constant

   109          % the RAW MON 200B interface and is newer than B02; DEFS is the authority for
   110          % this library layer. One file per layer - they do not compete.

  1491   (831)  
  1492   (832)          % THE JOIN IS ONE STEP, and a two-step handshake used to live here.
  1493   (833)          %
  1494   (834)          % It was added on the reading that "sending the join through XROUT does
  1495   (835)          % not put the nickname in front of the server" - that the server's
  1496   (836)          % connection port is handed a bare 4-byte connect, so a kHello reply was
  1497   (837)          % needed before the nickname could be sent. That reading was WRONG, and
  1498   (838)          % it was wrong because the SERVER was reading the wrong bytes: a letter
  1499   (839)          % arrives with its XSLET header still attached, and the server was
  1500   (840)          % parsing the header's serial number as a message kind.
  1501   (841)          %
  1502   (842)          % The nickname was in the first letter the whole time. sendJoin writes it
  1503   (843)          % after the header and the Programmer Guide is explicit that XROUT
  1504   (844)          % forwards it untouched. The server's WELCOME is the answer that hands
  1505   (845)          % over the magic number, which is all this side ever needed. See the
  1506   (846)          % header skip in CHATSV.PLNC for the layout and the manual reference.
  1507   (847)          %
  1508   (848)          % Nothing replaces this block: the welcome below already sets
  1509   (849)          % serverMagic, and always did.
  1510   (850)  
  1511   (851)          % ---- TRUST NOTHING THAT ARRIVED, ON THIS SIDE TOO ------------------
  1512   (852)          % The server checks exactly these three things before it reads a name or
  1513   (853)          % a text; this side did not, and the reasoning is identical. inBuf holds
  1514   (854)          % 256 bytes and PLANC checks no array bound:
  1515   (855)          %
  1516   (856)          %   nameLength is ONE BYTE, so it can say 255. The name loop would then
  1517   (857)          %   read inBuf(2)..inBuf(256) - past the end - and textAt would already
  1518   (858)          %   be 257 before any text was touched.
  1519   (859)          %
  1520   (860)          %   textLength is TWO BYTES, so it can say 65535, and the text loop
  1521   (861)          %   would walk tens of thousands of bytes off the end of the array.
  1522   (862)          %
  1523   (863)          %   A SHORT message is the quieter half: without testing against
  1524   (864)          %   readLength the loops print whatever the previous, longer message
  1525   (865)          %   left behind in inBuf.
  1526   (866)          %
  1527   (867)          % "The server would never send that" is not a reason. A truncated
  1528   (868)          % message does it by accident, and a client that only survives a
  1529   (869)          % well-behaved peer is not one worth writing.
  1530   (870)          % Both tests are against readLength, which the read below clamps to the
  1531   (871)          % size of inBuf - so a field that fits the MESSAGE also fits the ARRAY.
  1532   (872)          IF 2 + nameLength + 1 > readLength THEN
  1533   (873)              RETURN
  1534   (874)          ENDIF

  1536   (876)          2 + nameLength =: textAt
  1537   (877)          inBuf(textAt) * 256 + inBuf(textAt + 1) =: textLength
  1538   (878)          textAt + 2 =: textAt
  1539   (879)  
  1540   (880)          IF textAt + textLength > readLength THEN
  1541   (881)              RETURN
  1542   (882)          ENDIF

  1544   (884)          % The WELCOME is what reveals the server's address: everything after it

  2010  (1350)          % HOW THIS CLIENT WATCHES TWO THINGS WITHOUT A NO-WAIT TERMINAL.
  2011  (1351)          %

  2013  (1353)          % TNOWAIT (307B) so INBT stops blocking, then spin on keyboard and port

  2015  (1355)          % client is built the other way round and needs it not at all:
  2016  (1356)          %
